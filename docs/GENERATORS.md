# Генераторы: файлы, форматы, опции

`iolistgen generate` проверяет перечень и запускает генераторы. При ошибках в перечне файлы не
пишутся. Все генераторы работают с одной моделью имён ПЛК (`iolistgen/generators/plc.py`), поэтому
имя переменной в карте Modbus, в импорте SCADA и в перечне для документации совпадает с
объявлением в `GVL_IO`.

```bash
iolistgen generate docs/03_io_list.csv --out .            # всё: ST, карты, SCADA, тревоги, перечень
iolistgen generate docs/03_io_list.csv --out . --only st-codesys
iolistgen generate --list                                 # генераторы и опции
```

С `--out .` (корень проекта из шаблона) файлы ложатся по местам:

| Генератор | Файлы | Назначение |
|---|---|---|
| `st-codesys` | `src/GVLs/Generated/*.gvl.st`, `GVL_Persist.pvl.st`, `src/POUs/Generated/PRG_Devices/`, `PRG_ApplyProjectCfg/` | исходники ST в раскладке [LAYOUT.md](LAYOUT.md) |
| `modbus-map` | `docs/modbus_master_map.csv`, `docs/modbus_slave_map.csv`, `docs/modbus_map.md` | карта обмена Modbus: master и slave |
| `scada-csv` | `scada/scada_tags.csv`, `scada/scada_alarms.csv` | универсальный импорт тегов и тревог SCADA |
| `alarm-list` | `docs/alarms.csv` | список тревог проекта (контракт plc-process-lib, раздел 19) |
| `docs-table` | `docs/signal_list.md` | таблица «Перечень сигналов» |

**Общие правила.**

- Первая строка каждого файла — `AUTO-GENERATED by iolistgen <версия> — не редактировать;
  источник: <файл перечня>`, вторая — SHA-256 перечня и имя генератора (в ST — `//`, в Markdown —
  `<!-- -->`, в CSV — `#`). SHA-256 считается по содержимому таблицы (заголовок и строки данных),
  а не по байтам файла: пересохранение книги Excel без правок не меняет ни одного файла.
- Генерация идемпотентна и детерминирована: порядок — по модулям и каналам, адресам Modbus, `dev_no`;
  времени генерации в файлах нет. Файл перезаписывается, только если изменилось содержимое, поэтому
  повторный запуск ничего не меняет, а дифф в pull request показывает только изменения перечня.
  Время в заголовок добавляет только ключ `--timestamp` (тогда каждый запуск меняет все файлы).
- Опции задаются в `iolistgen.toml` (`[generators.<имя>]`) или ключом
  `--set <имя>.<опция>=<значение>`; полный список с умолчаниями — `iolistgen generate --list`.
- Генераторы ST и Markdown собирают текст шаблонами Jinja2 из `iolistgen/templates/`. Опция
  `template_dir` подставляет каталог своих шаблонов: файл с тем же именем перекрывает шаблон пакета.
- Генерация выполняется целиком или не выполняется: файлы всех генераторов собираются в памяти
  и пишутся, только если все генераторы отработали без ошибок (с `--strict` — и без
  предупреждений). Предупреждения генераторов (например, сверка `GVL_Persist`) печатаются перед
  списком файлов; ошибка генератора (конфликт имён) или два генератора на один файл — сообщение,
  код выхода 1, файлы не записаны.
- Сигнал без ФБ (роль `AUX`, [schema.md](schema.md#4-роли-сигналов)) получает переменную
  `GVL_IO`, строку карты Modbus, тег SCADA и строку перечня; экземпляра, Cmd, Cfg и тревог у него
  нет.

## `st-codesys` — исходники ST

Объекты по контракту plc-process-lib (разделы 1, 18.3, 20.6), папка проекта CODESYS `Generated`:

| Объект | Вид | Содержимое |
|---|---|---|
| `GVL_IO` | GVL, `qualified_only` | переменные сигналов: каналы модулей, значения Modbus, состояние слейвов, переменные адаптеров ПЧ |
| `GVL_DevIdx` | GVL `CONSTANT` | `<DEV> : UINT := dev_no` — номера устройств для SCADA и логики станции |
| `GVL_Hmi` | GVL | `st<DEV>Cmd : PL.ST_<Dev>Cmd` и импульс `xApplyProjectCfg` |
| `GVL_Persist` | Persistent Variables | `uiLayoutVersion`, затем по возрастанию `dev_no`: `st<DEV>Cfg` с уставками перечня, `st<DEV>Retain` (кроме AI/DI), затем данные приложения (`persist_extra`) |
| `GVL_CfgProject` | GVL `CONSTANT` | те же Cfg с теми же инициализаторами — «уставки проекта» |
| `GVL_Devices` | GVL | экземпляры `fb<DEV> : PL.FB_<Type>` без параметров, в том числе `PL.FB_PID` |
| `PRG_Devices` | PROGRAM | вызовы устройств: входы из `GVL_IO`, все `VAR_IN_OUT`, выходы в `GVL_IO`; у ПИД-регулятора — образец вызова в комментарии |
| `PRG_ApplyProjectCfg` | PROGRAM | `GVL_Persist.st<DEV>Cfg := GVL_CfgProject.st<DEV>Cfg;` — Retain не трогается |

### `GVL_IO`: адреса и слой ввода-вывода

Каналы модулей — **обычные переменные без `AT %I…`/`%Q…`**; их привязывают в дереве устройств
(I/O Mapping → «Map to existing variable»: `Application.GVL_IO.rLT101_mA`). Комментарий у каждой
переменной называет модуль и канал из перечня, тег, описание и шкалу. Почему так: в перечне —
имена модулей и номера каналов, а не адреса МЭК; адреса зависят от порядка модулей в дереве и
от таргета ПЛК210, а код без адресов не меняется при перестановке модулей. Те же переменные
пишет модель объекта в режиме симуляции (проект kns-pump-station).

| Раздел | Переменные | Кто пишет |
|---|---|---|
| входы модулей (DI, AI) | `x<TAG>`, `r<TAG>_mA` (AI 4–20 мА), `r<TAG>` (0…1, 0–10 В) | канал модуля |
| выходы модулей (DO, AO) | `x<TAG>`, `r<TAG>_mA` (позиционер) | `PRG_Devices` |
| Modbus, чтение / запись | тип перечня: `w<TAG>` WORD, `i<TAG>` INT, `r<TAG>` REAL, `x<TAG>` BOOL… | слой Modbus / `PRG_Devices` и адаптеры |
| сигналы AUX (в разделах выше по типу сигнала) | `x<TAG>`, `r<TAG>`, тип Modbus | канал или слой Modbus / код приложения (в комментарии — «без ФБ — код приложения») |
| состояние слейвов | `xMbOk_<линия>_S<слейв>` (TRUE — обмен исправен) | слой Modbus |
| адаптеры ПЧ → ФБ | `x<DEV>_CommOk`, `x<DEV>_VfdRun`, `x<DEV>_VfdReady`, `x<DEV>_VfdFault`, `r<DEV>_SpeedAct_pct` | адаптер ПЧ приложения |
| ФБ → адаптеры ПЧ | `r<DEV>_SpeedRef_pct`; при пуске по Modbus — `x<DEV>_VfdQRun`, `x<DEV>_VfdQReset` | `PRG_Devices` |

Значения Modbus объявлены в типе прибора (INT, REAL…), а не в виде регистров: их пишет и читает
слой Modbus — каналы конфигуратора Modbus в дереве устройств или код приложения. Порядок слов
32/64-битных значений указан в комментарии и в карте обмена. Слово состояния ПЧ разбирает, а
задание в единицах ПЧ пересчитывает адаптер приложения (`FB_VfdAdapter_<Model>`, контракт 14):
карты регистров ПЧ у разных моделей разные. У сигналов, которые обрабатывает адаптер (слова ПЧ,
задание и факт скорости — в том числе аналоговые AO/AI), комментарий заканчивается словами
«адаптер ПЧ»: в `PRG_Devices` их нет, это не пропуск. Имена в `GVL_IO` сравниваются без учёта регистра; конфликт
(тег `P101_COMMOK` и переменная адаптера `xP101_CommOk`) — ошибка генератора с именами обоих.

### `PRG_Devices`: вызовы

```st
// --- dev_no 11: P101 — Насос Н1 (MotorVfd) ---
// ПЧ: xCommOk, xVfd*, rSpeedAct_pct и rSpeedRef_pct — через адаптер приложения (GVL_IO.xP101_…)
GVL_Devices.fbP101(
    xExtFault     := GVL_IO.xP101_FLT,
    xLocal        := GVL_IO.xP101_LOC,
    xPowerOk      := GVL_Devices.fbPWR1.xValue,  // link_power
    xCommOk       := GVL_IO.xP101_CommOk,
    xVfdRunning   := GVL_IO.xP101_VfdRun,
    xVfdReady     := GVL_IO.xP101_VfdReady,
    xVfdFault     := GVL_IO.xP101_VfdFault,
    rSpeedAct_pct := GVL_IO.rP101_SpeedAct_pct,
    stCmd         := GVL_Hmi.stP101Cmd,
    stCfg         := GVL_Persist.stP101Cfg,
    stRetain      := GVL_Persist.stP101Retain);
GVL_IO.xP101_RUN          := GVL_Devices.fbP101.xQRun;
GVL_IO.rP101_SpeedRef_pct := GVL_Devices.fbP101.rSpeedRef_pct;
```

- Каждый вызов передаёт все `VAR_IN_OUT` (правило R1, иначе ошибка C0039); в `stCfg` — только
  переменная `GVL_Persist`, не константа (C0032).
- Передаются только входы сигналов перечня, ссылки `link_*` и `xChannelFault`; входы автоматики
  (`xAutoRun`, `xAutoOpen`, `wInterlock`, `wPermit…`, `rSpeedSpAuto_pct`, `rPosSpAuto_pct`) пишет
  логика станции до вызова `PRG_Devices` (R5).
- `xChannelFault` без строки `CHF`: `FALSE` у канала модуля, `NOT GVL_IO.xMbOk_…` у сигнала по
  Modbus (контракт 20.2). Со строкой `CHF` у значения по Modbus — `GVL_IO.x<TAG>_CHF OR NOT
  GVL_IO.xMbOk_…`: при потере связи бит отказа канала замирает вместе со значением, и без
  статуса обмена ФБ считал бы замёрзшее значение достоверным.
- Порядок: сначала устройства, на которые ссылаются `link_power` и `link_fb`, затем остальные по
  `dev_no`.
- Сигналы AUX устройства в вызов не входят (у ФБ нет такого входа): над вызовом — комментарий
  `// без входа ФБ (AUX, код приложения): GVL_IO.uiP101_FCODE — …`.
- ПИД-регулятор (тип `Pid`, [schema.md](schema.md#3-устройства-и-главная-строка)) не вызывается: у
  него нет сигналов перечня, а привязки `rPv_eu`, `xPvValid`, `xTrack`, `rOutAct_pct` — знание логики
  станции (контракт 17.3). На его месте в `PRG_Devices` — заголовок устройства и образец вызова в
  комментарии с `stCmd`, `stCfg`, `stRetain` (и `itfTime`, если задана опция `time_source`);
  экземпляр, Cmd, Cfg, Retain, блок Sts, теги и тревога PVF генерируются как у других устройств.
- `xValid` аналогового входа (`xPosFbValid := fb<LINK>.xValid` у `link_fb`, `xPvValid` ПИД в логике
  станции): в plc-process-lib 1.0.0 он FALSE не только при отказе, но и в защитных полосах NE 43
  (3,6…3,8 и 20,5…21 мА) после `tFailDelay` — значение там граница насыщения и для управления
  непригодно (решение AI-13 библиотеки). Привязка `xValid` к входам достоверности по-прежнему верна.
- Источник времени не привязывается — устройства берут встроенное системное время (контракт 20).
  Опция `time_source` передаёт `itfTime := <выражение>` всем устройствам (модель, `FB_FakeTime`).
  Опция `alarm_sink` добавляет в начало `PL.GVL_Lib.itfAlarmSink := <выражение>;` (контракт 5.3:
  присваивать каждый цикл).

### Конфигурация: `GVL_Persist`, `GVL_CfgProject`, `PRG_ApplyProjectCfg`

Начальные значения Cfg — из перечня: значения по умолчанию библиотеки, колонки, `params`, выводы из
состава устройства. Инициализатор пишет только поля, отличные от умолчаний DUT; массив `astAlarm`
или `astLimit` — целиком, если в нём изменилось хоть одно поле (контракт 18.3, правило 3).
Длинный инициализатор переносится по полю на строку, у элементов массивов — комментарий со слотом:

```st
    stLT101Cfg : PL.ST_AnalogInputCfg := (
        rRangeHi_eu := 5.0,
        tFilter := T#2S,
        astLimit := [
            (xEnable := TRUE, rSetpoint_eu := 4.5, tOnDelay := T#2S, tOffDelay := T#1S),  // 0 HH
            ...
```

После загрузки программы действуют сохранённые persistent-значения, а не начальные. Изменённые в
перечне уставки попадают в контроллер командой HMI `GVL_Hmi.xApplyProjectCfg` (её обрабатывает
`PRG_Devices`) или вызовом `PRG_ApplyProjectCfg` из логики станции: Cfg копируются из
`GVL_CfgProject`, режимы, моточасы и пуски (`st<DEV>Retain`) не меняются.

Имена констант `GVL_CfgProject` — как у `GVL_Persist` (`st<DEV>Cfg`, контракт 18.3). Правило
st_lint STL007 требует у констант UPPER_SNAKE_CASE, поэтому перед каждой стоит подавление
`// lint:allow STL007 …` с причиной.

**Сверка с предыдущим `GVL_Persist`** (опция `persist_check`, контракт 18.3, правило 1): если в
каталоге вывода уже есть `GVL_Persist.pvl.st`, генератор сравнивает с ним новый список и
предупреждает, если тип переменной изменился (CODESYS переинициализирует её целиком), переменная
удалена (её сохранённые значения пропадут), у `dev_no` другое устройство (переименование или
переиспользование номера: данные прежнего имени к новому не перейдут) или новое устройство
получило номер меньше прежних (по правилу новые устройства встают в конец). С `--strict` любое из
этих предупреждений отменяет запись файлов (код выхода 1) — так сверку стоит запускать в CI.

### Данные приложения в `GVL_Persist`: `persist_extra`

Persistent-данные нужны не только устройствам. Задание оператора ПИД-регулятора лежит в
`GVL_Hmi.st<DEV>Cmd.rSp_eu` — обычной переменной, и после перезапуска ПЛК пропало бы; уставки
станции тоже должны переживать загрузку программы (контракт 18.3, правило 9). Руками
сгенерированный `GVL_Persist` не правится: такие переменные перечисляются в файле проекта, а
генератор дописывает их после устройств под заголовком `// --- данные приложения, persist_extra`:

```text
// examples/kns/persist_extra.txt — по объявлению на строку, комментарии «//» пропускаются
rLIC101SpOper_m : REAL := 2.0;   // задание оператора регулятора уровня LIC101, м
```

Формат — UTF-8, одно объявление ST на строку (`имя : тип := значение; // комментарий`), значение
и комментарий необязательны. Имя — идентификатор ST, не совпадающее с переменными, которые
генератор объявляет сам (`uiLayoutVersion`, `st<DEV>Cfg`, `st<DEV>Retain`): иначе ошибка
генератора с номером строки. Порядок постоянный, как у устройств: новые переменные — только в
конец файла. `persist_check` сверяет данные приложения с прошлым `GVL_Persist` и предупреждает о
перестановке, о новой переменной перед прежними, о смене типа и об удалении; с `--strict` любое из
этих предупреждений отменяет запись. Копировать значения между `GVL_Persist` и командами (например,
`rSp_eu` регулятора) — задача логики станции.

### Ручной код — вне `Generated`

Генератор пишет только свои десять файлов и чужие не трогает. Ручной код проекта лежит рядом в
своих папках, например:

| Папка | Что |
|---|---|
| `src/POUs/Station/` | логика станции: режимы, чередование, АВР, входы автоматики устройств |
| `src/POUs/Adapters/` | адаптеры ПЧ `FB_VfdAdapter_<Model>`, слой Modbus |
| `src/GVLs/Station/` | переменные станции |

В задаче логика станции вызывается до `PRG_Devices` (контракт 1). Правка сгенерированного файла
пропадёт при следующей генерации — меняйте перечень, `iolistgen.toml` или шаблон.

## `modbus-map` — карта обмена Modbus

**Master** (`modbus_master_map.csv`) — сигналы MB перечня по линии, слейву, области и адресу:

| Колонка | Смысл |
|---|---|
| `link`, `slave` | линия и адрес слейва |
| `function`, `function_name`, `area` | функция Modbus и область (0x, 1x, 3x, 4x) |
| `address`, `bit`, `length` | адрес PDU с нуля, бит регистра, длина в регистрах или катушках |
| `data_type`, `word_order` | тип значения и порядок слов (HL, LH) у 32/64-битных |
| `direction` | чтение или запись (по функции) |
| `tag`, `description`, `device`, `role` | сигнал перечня |
| `plc_variable` | переменная `GVL_IO` |
| `eng_min`, `eng_max`, `units`, `raw_min`, `raw_max`, `scaling` | шкала; `raw_*` — только у AI с `eInput = Raw` (`rRawLo_cnt`, `rRawHi_cnt`) |

Сигналы AUX тоже входят в карту master (роль `AUX`, `device` — устройство или пусто, в `scaling`
— «сигнал без ФБ — значение читает и пишет код приложения»): их адреса участвуют в проверке
пересечений, как и остальные.

**Slave** (`modbus_slave_map.csv`) — блоки `stSts` устройств для SCADA (контракт 4.6): регистр n
блока — байты 2n…2n+1 структуры, 32-битные поля выровнены по 4 байтам, первым идёт `stCommon` с
`eDevType`. Колонки: `dev_no`, `device`, `device_type`, `function`, `area`, `address`, `offset`
(регистр от начала блока), `length`, `data_type` (перечисления — INT), `word_order` (у 32-битных),
`field`, `description`, `units` (у полей `_eu` AI и ПИД — единицы PV из перечня), `plc_path`.
Размеры блоков (22, 15, 34, 26, у ПИД — 32 регистра) сверены с таблицей 4.6 тестом. Регистр 13
общего заголовка — `stCommon.wAlmSuppressed` (бит i — слот подавлен логикой, SuppressedByDesign;
в 1.0.0 заменил резерв `wReserve`), регистр 10 `wAlmShelved` — только отложенные оператором.

`modbus_map.md` — обе карты для документации: таблица master, таблица блоков slave и раскладка
каждой структуры `stSts`.

| Опция | По умолчанию | Смысл |
|---|---|---|
| `dir` | `docs` | каталог файлов |
| `master_csv`, `slave_csv`, `markdown` | `modbus_master_map.csv`, `modbus_slave_map.csv`, `modbus_map.md` | имена файлов |
| `delimiter` | `;` | разделитель CSV: `;`, `,`, `tab` |
| `comment_header` | `true` | строки `# AUTO-GENERATED …` в начале CSV |
| `slave` | `true` | писать карту slave |
| `slave_area` | `holding` | `holding` (4x, FC3) или `input` (3x, FC4) |
| `slave_base` | `0` | адрес первого блока |
| `slave_layout` | `packed` | `packed` — блоки подряд по `dev_no`; `dev_no` — адрес = `slave_base + dev_no · slave_stride` (адреса не сдвигаются при удалении устройств) |
| `slave_stride` | `40` | шаг блоков при `slave_layout = dev_no`; не меньше самого длинного блока (34) |
| `slave_word_order` | `LH` | порядок слов 32-битных полей в образе slave |
| `application` | `Application` | имя приложения CODESYS в путях |
| `template_dir` | — | свои шаблоны Jinja2 |

Порядок слов `LH` по умолчанию — то, что даёт копирование памяти структуры на ПЛК с прямым
порядком байт (x86, ARM): младшее слово первым. Способ копирования `stSts` в образ регистров и
порядок слов — задача адаптера обмена приложения (открытый вопрос O5 контракта); карта записывает
принятое решение. Команды SCADA по Modbus в карту не входят: только через адаптер, импульс по
фронту (контракт 2.1).

## `scada-csv` — импорт тегов SCADA

`scada_tags.csv` — тег на строку. Состояние SCADA читает из `stSts` экземпляра
(`Application.GVL_Devices.fbLT101.stSts.rValue_eu`) или выходов ФБ (`fbLS101.xValue`), команды
пишет в `GVL_Hmi.st<DEV>Cmd` (снаружи `VAR_IN_OUT` экземпляра недоступен, контракт R2).

| Колонка | Смысл |
|---|---|
| `tag` | `<DEV>.<точка>`: `LT101.Value`, `P101.Cmd.Start` (разделитель — опция `separator`) |
| `description` | описание устройства и точки |
| `device`, `dev_no`, `device_type`, `hmi_group` | устройство |
| `data_type`, `access` | тип IEC (перечисления — INT), `R` или `RW` |
| `units`, `eng_min`, `eng_max` | единицы и шкала (у значения AI — из перечня) |
| `alarm_hh`, `alarm_h`, `alarm_l`, `alarm_ll`, `alarm_priority` | уставки и приоритет у значения AI |
| `plc_path` | путь переменной: `Application.GVL_Devices.fbLT101.stSts.rValue_eu` |
| `opcua_node_id` | узел OPC UA сервера CODESYS: `ns=4;s=\|var\|CODESYS Control Win V3.Application.…` |

Точки по типам устройств: общий заголовок (`Mode`, `Ne107`, `Status`, `Fault`, `Warning`,
`CfgErr`, `AlmActive`, `AlmUnack`, `AlmShelved` — отложены оператором, `AlmSuppressed` — подавлены
логикой, `PrioUnack`, `CmdResult`, `CmdSeq`, `DevType`) и
общие команды (`Cmd.SetAuto`, `Cmd.SetManual`, `Cmd.SetOos`, `Cmd.Reset`, `Cmd.Ack`, маски
`Cmd.AckReq`, `Cmd.ShelveReq`, `Cmd.UnshelveReq`); AI — `Value`, `ValuePct`, `Valid`, `Raw`,
`Signal`, `SubstRemain`, `Cmd.SubstValue`; DI — `Value`, `Valid`, `SubstRemain`,
`Cmd.SubstValue`; двигатель — `Running`, `State`, блокировки, счётчики, `Cmd.Start`, `Cmd.Stop`,
`Cmd.ResetMaint` (ПЧ — ещё `SpeedRef`, `SpeedAct`, `SpeedAutoActive`, `Cmd.SpeedSp`); арматура —
`Opened`, `Closed`, `State`, блокировки, счётчики, `Cmd.Open`, `Cmd.Close`, `Cmd.Stop` (только у
задвижки с приводом); регулирующий клапан — `Out`, `OutmA`, `PosSp`, `PosFb`, `Deviation`,
`AutoActive`, `Cmd.PosSpMan`; ПИД-регулятор — `Sp`, `SpTarget`, `Pv` (единицы и шкала — диапазон PV),
`Err`, `Out`, `P`, `I`, `D`, `Dt`, `SatHigh`, `SatLow`, `Cmd.Sp`, `Cmd.ManualOut`.

Сигнал без ФБ (роль `AUX`) — один тег с именем тега перечня (`HL1`, `P101_FCODE`): переменная
`GVL_IO` (`plc_path` — `Application.GVL_IO.xHL1`), доступ `R`, единицы и шкала из перечня. Тег
идёт после тегов своего устройства, простые сигналы (AUX без устройства) — в конце файла. Выход
AUX SCADA только читает: его пишет код приложения.

`scada_alarms.csv` — тревоги для SCADA: `id`, `code`, `device`, `slot`, `priority`, `text` и где
их видно: бит `slot` в словах `active_tag` (`<DEV>.AlmActive`) и `unack_tag` (`<DEV>.AlmUnack`),
квитирование — бит `slot` в `ack_tag` (`<DEV>.Cmd.AckReq`); `setpoint`, `delay_s`.

Номер пространства имён (`opcua_namespace`, 4) и имя устройства в идентификаторе узла
(`opcua_device`) зависят от рантайма и версии CODESYS — **сверить по обзору сервера** (UaExpert):
на ПЛК210 имя устройства другое. Переменные видны клиентам OPC UA, если `GVL_Devices` и `GVL_Hmi`
(для тегов AUX — ещё `GVL_IO`) отмечены в символьной конфигурации (docs/MANUAL_STEPS.md).

| Опция | По умолчанию | Смысл |
|---|---|---|
| `dir` | `scada` | каталог файлов |
| `tags_csv`, `alarms_csv` | `scada_tags.csv`, `scada_alarms.csv` | имена файлов; пустой `alarms_csv` — без тревог |
| `delimiter`, `comment_header` | `;`, `true` | как у `modbus-map` |
| `separator` | `.` | разделитель частей имени тега: `.` или `_` |
| `commands` | `true` | теги команд (запись) |
| `aux_signals` | `true` | теги сигналов без ФБ (роль AUX): переменные `GVL_IO`, чтение |
| `diagnostics` | `true` | теги общего заголовка и общих команд |
| `application` | `Application` | имя приложения CODESYS |
| `opcua_namespace` | `4` | номер пространства имён OPC UA |
| `opcua_device` | `CODESYS Control Win V3` | имя устройства в узле OPC UA; пусто — колонка пустая |
| `templates` | шаблоны пакета | шаблоны текстов тревог (как у `alarm-list`) |

### MasterSCADA 4D и другие SCADA

Документированного формата импорта тегов MasterSCADA 4D не найдено (справка вендора, IEK Digital,
проверено 2026-10-16):

- переменные OPC UA сервера CODESYS добавляются **обзором сервера** в диалоге подключения
  («Подключиться без загрузки» или «Загрузить все», выбор параметров, «Применить»), импорта из
  файла на странице нет — [справка](https://help.iek-digital.ru/Help-web/dialog_podklyucheniya_k_serveru_opc_ua.html);
- каналы Modbus импортируются в редактор каналов из xlsx «собственного формата, совместимого с
  операцией экспорта»; названы колонки таблицы («Имя канала», «Регион», «Адрес», «Тип в
  устройстве», «Тип в SCADA», «Доступ», «Комментарий»…), раскладка файла не описана —
  [справка](https://help.iek-digital.ru/Help-web/dialog_importa_kanalov_modbus1.html);
- табличное представление проекта правится экспортом и импортом CSV, набор столбцов задаёт запрос —
  [справка](https://help.iek-digital.ru/Help-web/redact_rez_zaprosov_csv.html).

Поэтому вместо придуманного формата — заготовка плагина
[`plugins/iolistgen-masterscada4d/`](../plugins/iolistgen-masterscada4d/README.md): генератор
`masterscada4d` находится точкой входа, но файлов не пишет и объясняет почему; в коде — TODO с тем,
что нужно для реализации (образец экспорта xlsx из MasterSCADA 4D). Пока для MasterSCADA 4D —
`scada-csv` (сверка путей и узлов с обзором сервера) и карта slave `modbus-map`.

## `alarm-list` — список тревог

`docs/alarms.csv` в колонках контракта (раздел 19): `id` (`dev_no · 10 + слот`), `code`
(`<DEV>.<SUFFIX>`), `tag`, `slot`, `priority` (из итоговой Cfg), `text_ru`, `cause`,
`consequence`, `operator_action`, `setpoint` (у пределов AI), `delay_s` (логическая задержка плюс
задержка тревоги).

В список не входят слоты с приоритетом `None` и слоты, условие которых при этом составе
устройства не возникает: контроль ОС двигателя без ОС, «не открылась» у арматуры без концевика
«открыто», «оба концевика» без двух концевиков, муфта без `xTorqueUsed`, внешняя авария без строки
`FAULT`, выход за диапазон у входа без NE 43 (`Norm01`, `Eng`, `Raw`), отказ канала DI без строки
`CHF` и не по Modbus, рассогласование ПЧ при `rSpeedDev_pct = 0`, рассогласование и отказ ОС
регулирующего клапана без ОС, авария позиционера без строки `POS_FAULT`.

Текст — «описание устройства: текст шаблона», причина, последствие и действие оператора — из того
же шаблона. Шаблоны по умолчанию — копия `docs/alarm_templates.csv` выпуска plc-process-lib 1.0.0 в
пакете (`iolistgen/data/alarm_templates.csv`, колонки `type;slot;suffix;text_ru;operator_action;
cause;consequence`, по строке на каждый слот каждого типа); у `MotorVfd` берутся шаблоны `MotorVfd`
(слоты 6–7), затем `Motor`. Копия совпадает с файлом библиотеки, кроме двух строк, где в файле 1.0.0
сдвинуты колонки (COM у `MotorVfd`, BLS у `Valve`: причина записана через запятую в колонке
действия оператора) — их сверяет `tests_support/check_library.py`. Опция `templates` задаёт свой
файл того же формата (например, файл библиотеки по `build_from_repo`), `none` — без шаблонов:
текст «описание устройства: смысл слота» из каталога, без причины и действия.

| Опция | По умолчанию | Смысл |
|---|---|---|
| `filename` | `docs/alarms.csv` | файл |
| `delimiter`, `comment_header` | `;`, `true` | как у `modbus-map` |
| `templates` | шаблоны пакета | файл шаблонов текстов тревог; `none` — без шаблонов; относительный путь из `iolistgen.toml` — от его каталога |

## Проверка ST без CODESYS

Настоящая проверка — сборка в CODESYS 3.5.17.30 с библиотекой plc-process-lib 1.0.0.0: код по
перечню КНС-1 в `src/` этого репозитория собран без ошибок и предупреждений, Cfg всех устройств
приняты `CheckConfig` библиотеки ([README, «Тесты и качество»](../README.md#тесты-и-качество);
[TEST_REPORT.md](TEST_REPORT.md)). Без CODESYS — на любом ПК и в CI — сгенерированный код проверяется так
(`python tests_support/check_generated_st.py`, в CI — задание RuSTy):

1. **st_lint** (`tools/check/st_lint.py --strict`) — префиксы, заголовки POU, длина строк,
   нормализация, «магические числа»: сгенерированный код проходит без замечаний.
2. **assemble** — раскладка и заголовки объектов (stlayout).
3. **RuSTy** `plc --check` (1.0.6) — разбор и проверка типов по заглушке библиотеки
   `tests_support/pl_stub/`: DUT (перечисления, Cmd, Cfg с умолчаниями, Sts, Retain), интерфейсы
   `I_TimeSource` и `I_AlarmSink`, `GVL_Const`, `GVL_Lib` и ФБ устройств с теми же входами, выходами
   и `VAR_IN_OUT`, что в выпуске 1.0.0, без тел. Тест `pytests/test_pl_stub.py` сверяет заглушку с
   каталогом пакета, а `tests_support/check_library.py` (тест `pytests/test_library_source.py`) —
   каталог и каждый объект заглушки с исходниками библиотеки (`PL_REPO` или `../plc-process-lib`).

Перед RuSTy копия раскладки меняется только там, где RuSTy не понимает конструкцию CODESYS:
`VAR_IN_OUT CONSTANT` → `VAR_IN_OUT` в заглушке (RuSTy: E034) и `GVL_CfgProject.st<DEV>Cfg` →
`st<DEV>CfgPrj` (RuSTy не различает имена GVL, шаблон убирает `GVL_Имя.`). Случаи проверки:
`kns_mini.csv` с опциями по умолчанию, `gen_fixture.csv` (все роли и виды привязок) с
`time_source` и `alarm_sink`, перечень КНС-1 из `examples/kns/` (с сигналами AUX) и
синтетический на 300 сигналов; ключ `--list ПЕРЕЧЕНЬ` проверяет любой перечень (с
`iolistgen.toml` рядом с ним, как у команды `iolistgen`), ключ `--repo` — раскладку `src/` этого
репозитория (пример КНС-1 и `PRG_Main`) без генерации.

**Что RuSTy ловит** (отрицательный контроль в `pytests/test_st_check.py`): неизвестный вход ФБ,
пропущенный `VAR_IN_OUT` (E030), чужую Cfg или Cmd в параметре (E037), несуществующую переменную
или поле Cfg (E048), неизвестное значение перечисления. **Чего не ловит**: неявное `REAL → BOOL`,
литерал `REAL` в поле `TIME`, правила CODESYS вроде C0032 (литерал в `VAR_IN_OUT CONSTANT`) — их
проверяют тесты генератора (типизированные литералы каталога, только переменные в `stCfg`) и
сборка в CODESYS.
